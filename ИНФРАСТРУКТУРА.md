# Как устроен сервер — где что лежит и как работает

Справочник по продакшн-окружению Telegram-бота продажи билетов. Если что-то
здесь устарело после будущих изменений — поправьте заодно и этот файл.

## Сервер

- Хостинг: **Timeweb**, VM с именем `spb-3-vm-yjv2` (Санкт-Петербург).
- На этом же сервере уже жил и продолжает работать **MAX-бот** (другой проект,
  для мессенджера MAX, не Telegram) — он не трогается, всё новое ставилось
  рядом, в отдельных папках/процессах/базе, чтобы не задеть его работу.
- MAX-бот устроен иначе, чем наш проект, и это легко забыть: он лежит в
  `/home/maxbot/max-bot`, работает под пользователем `maxbot`, запускается
  службой systemd `max-bot.service` (не pm2) и стартует из собранного `dist/`.
  Поэтому правка его кода требует трёх шагов: скопировать файл, собрать
  (`sudo -u maxbot bash -lc 'cd ~/max-bot && npm run build'`) и перезапустить
  (`systemctl restart max-bot`). База у него своя — управляемая `default_db`
  в Timeweb, а не наш локальный Postgres.
- Заходить на сервер — по SSH, под пользователем `root` (или `maxbot`, если
  так исторически настроен доступ).

## Где лежит код

- Наш проект: `~/telegrambot` (папка `/root/telegrambot`, если зашли под root).
- MAX-бот: `~/max-bot` (соседняя папка, не наша зона ответственности).
- Репозиторий: `https://github.com/Bernovv/telegrambot.git`, рабочая ветка
  `codex/phase-1-foundation`.
- Файл с реальными секретами: `~/telegrambot/.env` — **не в git**
  (`.gitignore` это гарантирует). Копия этого файла также лежит у вас на
  компьютере в папке `BusinessProriv/telegrambot/.env` — именно оттуда его
  надо копировать на сервер, если он меняется.

## Node.js — две версии на одном сервере

- Системный Node (из `apt`, версия 20.x) — использует **MAX-бот**. Не трогаем.
- Наш проект требует Node **24+**. Поставлен отдельно через `nvm` в
  `~/.nvm`, никак не пересекается с системным.
- Скрипты запуска (`deploy/run-bot.sh`, `run-api.sh`, `run-worker.sh`) сами
  подключают nvm и Node 24 внутри себя — поэтому неважно, что стоит в PATH
  снаружи, конфликта с MAX-ботом не будет.

## База данных

Не используем ни приватный, ни публичный адрес управляемой базы Timeweb,
которой пользуется MAX-бот (`default_db`) — по двум причинам:

1. Тариф Timeweb разрешает только одну базу в этом managed-кластере — создать
   вторую нельзя без платного апгрейда.
2. У `default_db` та же доменная модель, что и у нашего проекта (`users`,
   `orders`, `wallet_accounts` и т.д. с реальными данными MAX-бота) — писать
   туда нашими миграциями было бы опасно.

Поэтому на сервере установлен **свой, отдельный Postgres** (версия 18, через
`apt install postgresql`), который слушает только `127.0.0.1:5432` — то есть
доступен исключительно с этого же сервера, снаружи недоступен.

- База: `telegram_bot_db`
- Пользователь: `telegram_bot_app`
- Пароль: см. `.env` → `DATABASE_URL`
- Строка подключения в `.env`:
  `DATABASE_URL=postgresql://telegram_bot_app:<пароль>@127.0.0.1:5432/telegram_bot_db`

Проверить подключение вручную:

```bash
PGPASSWORD='<пароль_из_.env>' psql -h 127.0.0.1 -U telegram_bot_app -d telegram_bot_db -c "\dt"
```

Применить миграции (если появятся новые):

```bash
cd ~/telegrambot
export NVM_DIR="$HOME/.nvm"; [ -s "$NVM_DIR/nvm.sh" ] && \. "$NVM_DIR/nvm.sh"
node --env-file=.env --import tsx packages/database/scripts/migrate.ts deploy
```

## Процессы приложения

Запускаются и живут через **pm2** под пользователем `root`. MAX-бота в этом
списке нет и быть не должно — он под systemd и другим пользователем (см. выше):

| Имя в pm2 | Что делает | Скрипт запуска |
|---|---|---|
| `bot` | Сам Telegram-бот: меню, покупка билета в чате, long-polling | `deploy/run-bot.sh` |
| `api` | Принимает вебхуки об оплате от Т-Банка и запросы админ-панели, слушает `127.0.0.1:3001` | `deploy/run-api.sh` |
| `worker` | Фоновые задачи: доставка билета после оплаты, уведомления, снятие брони, напоминания | `deploy/run-worker.sh` |
| `admin` | Админ-панель на Next.js, слушает `127.0.0.1:3002` | `deploy/run-admin.sh` |
| `tg-account` | Аккаунт компании в Telegram: принимает входящие в переписку и забирает вложения | `deploy/run-tg-account.sh` |

Полезные команды:

```bash
pm2 status                              # статус наших процессов
pm2 logs bot --lines 50 --nostream      # последние логи бота
pm2 logs api --lines 50 --nostream
pm2 logs worker --lines 50 --nostream
pm2 logs admin --lines 50 --nostream
pm2 logs tg-account --lines 50 --nostream
pm2 restart bot api worker admin        # перезапустить после обновления кода/.env
pm2 restart tg-account                  # аккаунт компании — отдельно, он живёт своей жизнью
pm2 save                                # сохранить текущий список процессов (чтобы поднялись после перезагрузки сервера)
```

Порты заняты так: `3000` — MAX-бот (не наш), `3001` — наш `api`, `3002` —
админ-панель. Поэтому в `run-admin.sh` порт задан флагом `-p 3002`: в `.env`
переменная `PORT` равна 3001, и если Next её подхватит, он займёт порт API и
Т-Банк перестанет доставлять уведомления об оплате.

### Панель после обновления кода надо пересобирать

`bot`, `api`, `worker` и `tg-account` запускаются из исходников через `tsx`,
поэтому им хватает `pm2 restart`. Панель — нет: `next start` запускает уже собранные
файлы. После каждого обновления кода панели:

```bash
cd ~/telegrambot
export NVM_DIR="$HOME/.nvm"; [ -s "$NVM_DIR/nvm.sh" ] && \. "$NVM_DIR/nvm.sh"
export NEXT_PUBLIC_SUPABASE_URL=$(grep -m1 '^NEXT_PUBLIC_SUPABASE_URL=' .env | cut -d= -f2-)
export NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=$(grep -m1 '^NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=' .env | cut -d= -f2-)
corepack pnpm install --frozen-lockfile
corepack pnpm --filter @ticket-platform/admin-web build
pm2 restart admin
```

Переменные `NEXT_PUBLIC_*` выставляются перед сборкой не для красоты: Next
вшивает их в собранные файлы, а не читает при запуске. Собрали без них —
получите панель, которая не знает адреса Supabase и показывает пустой экран
входа.

Загружать `.env` целиком командой `. ./.env` нельзя: пароль Т-Банка содержит
`&`, и шелл на нём спотыкается. Процессы этой проблемы не знают, потому что
читают файл разборщиком Node (`node --env-file`).

## Файл подкачки

На сервере около гигабайта оперативной памяти, и установка зависимостей панели
(Next и его бинарники) в него не помещалась — процесс убивало ядро с `Killed`.
Добавлены 2 ГБ подкачки в `/swapfile`, запись в `/etc/fstab` есть, так что
после перезагрузки подключится сама. Проверить: `free -h`, строка `Swap`.

## nginx и домены

Доменов два: `max-bot.biz-day.ru` — для платёжных вебхуков (там же живёт
MAX-бот), и `admin.biz-day.ru` — для админ-панели.

### Вебхуки Т-Банка

Отдельного домена для бота нет и не нужно — используется уже готовый
домен MAX-бота `max-bot.biz-day.ru` (HTTPS уже настроен через Let's Encrypt).
В конфиг nginx (`/etc/nginx/sites-available/max-bot`) добавлен ещё один
`location`, специально для приёма платёжных вебхуков от Т-Банка:

```nginx
location /webhooks/payments/tbank {
    proxy_pass http://127.0.0.1:3001;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

Т-Банк присылает уведомления об оплате на
`https://max-bot.biz-day.ru/webhooks/payments/tbank`, nginx перенаправляет их
на наш процесс `api` (порт 3001). Общий `location /` в этом же файле
по-прежнему ведёт на MAX-бота (порт 3000) — эти два `location` не мешают друг
другу (более специфичный путь у nginx всегда в приоритете).

### Оферта

PDF оферты лежит на сервере и отдаётся по постоянному адресу
`https://max-bot.biz-day.ru/offer/business-picnic-2026-v1.pdf`. Файл и его контрольная сумма
записаны в базе (`offer_versions`), бот берёт ссылку оттуда, а не из кода — иначе нельзя
доказать, с какой редакцией согласился покупатель.

Файл на сервере: `/var/www/offer/business-picnic-2026-v1.pdf`, исходник — в репозитории,
`deploy/offer-business-picnic-2026-v1.pdf`.

```nginx
location /offer/ {
    alias /var/www/offer/;
    add_header Content-Disposition "inline";
    types { application/pdf pdf; }
    default_type application/pdf;
}
```

Новая редакция оферты — это **новая версия**, а не подмена файла: кладём файл с новым именем,
добавляем строку в `offer_versions` с его sha256 и переключаем `active_offer_version_id`.
Подменять файл по существующему адресу нельзя — старые согласия перестанут соответствовать
документу.

## Вход в админ-панель

Пароли администраторов у нас не хранятся: вход, пароль и второй фактор — на
стороне Supabase (проект `hyaqtdwhpivdmxodorrj`), а права лежат в нашей базе,
в таблицах `admin_accounts` и `admin_role_grants`. Связаны они полем
`auth_subject` — это UID пользователя в Supabase.

Отсюда два следствия, которые легко забыть:

- Если пользователя в Supabase пересоздать, у него будет новый UID, и права
  «отвяжутся». Лечится обновлением `auth_subject` в `admin_accounts`, а не
  повторным запуском скрипта — он срабатывает единственный раз, пока в базе
  нет ни одного администратора.
- Второй фактор сейчас **выключен** переменными `ADMIN_MFA_REQUIRED=false` и
  `NEXT_PUBLIC_ADMIN_MFA_REQUIRED=false`: входа по паролю достаточно, включая
  подтверждение оплаты, возврат и правку кошелька. Механика входа по коду при
  этом на месте — включается теми же двумя переменными.
- Переменных две, и значение у них должно совпадать. Первую читает `api` при
  запуске, вторую панель вшивает в сборку: после её правки панель надо
  пересобрать, `pm2 restart admin` не поможет. Разойдутся — панель пустит без
  кода, а `api` откажет в денежных операциях.
- Когда фактор включён, обязателен он не всем: роли `super_admin` и
  `financial_admin` помечены в базе как требующие MFA, а денежные разрешения
  требуют его у кого угодно. Потерян телефон — удалите MFA-фактор у пользователя
  в Supabase, панель предложит настроить заново.

## Telegram API заблокирован — прокси через Cloudflare Worker

С этого сервера (РФ) `api.telegram.org` недоступен напрямую (таймауты).
Решение — бесплатный Cloudflare Worker, который просто перекладывает запросы
в Telegram (сам Cloudflare для российских провайдеров не заблокирован):

- Код воркера: `deploy/cloudflare-telegram-proxy.js` в репозитории (для
  справки/пересоздания, если понадобится).
- Адрес развёрнутого воркера прописан в `.env` → `TELEGRAM_API_ROOT`.
- Секретов внутри воркера нет — токен бота передаётся в самом URL запроса,
  как обычно у Telegram Bot API, воркер его не хранит.
- Если воркер когда-нибудь пересоздадите — обновите `TELEGRAM_API_ROOT` в
  `.env` на новый адрес и сделайте `pm2 restart bot api worker`.

## Аккаунт компании в Telegram и прокси для него

Второй канал Telegram, помимо бота: обычный аккаунт на корпоративном номере, от
имени которого менеджеры отвечают из панели. Живёт по MTProto, а не по Bot API.

**Cloudflare-воркер выше ему не помогает.** Тот перекладывает HTTP-запросы Bot
API, а MTProto — сырой TCP с постоянным соединением, и входа для TCP у Worker
нет. Поэтому у аккаунта свой прокси на отдельной зарубежной машине.

### Машина прокси

| Что | Значение |
|---|---|
| Провайдер | Timeweb Cloud, Амстердам |
| Имя | `ams-1-vm-smbv` |
| Адрес | `185.11.135.121`, вход по SSH под `root` |
| ОС | Ubuntu 24.04, 1 ядро / 1 ГБ / 15 ГБ |
| Стоимость | 710 ₽/мес (510 конфигурация + 200 публичный IPv4) |
| Что стоит | `dante-server`, systemd-служба `danted` |
| Порт | 11080, SOCKS5 с логином и паролем |
| Пользователь | `tgproxy` (системный, без оболочки; пароль — в `.env` нашего сервера) |

На машине нет ничего, кроме прокси: ни данных, ни резервных копий. Настройка —
это `/etc/danted.conf` на двадцать строк и четыре правила `ufw`; при утрате
машины всё восстанавливается за десять минут по
`docs/runbooks/telegram-account.md`.

**Файрвол пускает на 11080 только `185.178.44.145`** — наш сервер. Открытый
SOCKS-прокси находят сканерами за сутки, и ходить через него начинают чужие, а
отвечает за это владелец адреса.

Проверка живости с нашего сервера (пароль — из `TELEGRAM_ACCOUNT_PROXY`):

```bash
curl -x socks5h://tgproxy:ПАРОЛЬ@185.11.135.121:11080 https://api.ipify.org
```

Должен ответить `185.11.135.121`. Ответил нашим адресом — запрос пошёл мимо
прокси; завис — прокси не пускает.

## Если что-то не работает — с чего начать

1. `pm2 status` — все четыре процесса (`bot`, `api`, `worker`, `admin`) должны
   быть `online`, счётчик `↺` не должен расти на глазах (это значит процесс
   постоянно падает и перезапускается). Большое число в `↺` само по себе ни о
   чём не говорит — оно копится за всю историю и может остаться от давно
   починенной поломки.
2. `pm2 logs <имя> --lines 50 --nostream` — смотреть на `error.log`, там
   теперь пишется не только тип ошибки, но и текст сообщения.
3. Проверить, что `.env` на сервере совпадает с тем, что должно быть (частая
   причина проблем — забыли обновить `.env` на сервере после того, как он
   поменялся локально). `grep -n ИМЯ_ПЕРЕМЕННОЙ .env` — если пусто, значит
   переменной нет вообще (например, `sed` по отсутствующей строке ничего не
   сделает и не пожалуется).
4. Проверка доступности Telegram через прокси:
   `curl -s "$(grep TELEGRAM_API_ROOT .env | cut -d= -f2)/bot$(grep TELEGRAM_BOT_TOKEN .env | cut -d= -f2)/getMe"`
   — должен вернуть `{"ok":true,...}`.
5. Панель не открывается — сначала проверьте её саму, минуя nginx:
   `curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:3002/login`.
   `200` означает, что дело в nginx или сертификате, а не в панели.
6. Настоящую причину отказа при входе видно в браузере: F12 → Network →
   запрос `token?grant_type=password`, поле `code` в ответе.

### Служебные команды

Запускать из `~/telegrambot` под Node 24 (`export NVM_DIR="$HOME/.nvm"; . "$NVM_DIR/nvm.sh"`).

```bash
corepack pnpm env:check          # заполнены ли обязательные переменные в .env
corepack pnpm queue:dead-letter  # что застряло в доставке и не дойдёт само
corepack pnpm price:show         # текущие тарифы мероприятия
corepack pnpm broadcast:status   # состояние рассылок, в том числе зависших
```

`env:check` стоит выполнять **сразу после каждого копирования `.env` на сервер** — он ловит
ровно ту ошибку, из-за которой 27 июля затёрся адрес прокси и на два часа встала доставка.

`queue:dead-letter` показывает задачи, исчерпавшие все попытки. Такое возможно при сбое
дольше трёх часов. Вернуть их в работу: `corepack pnpm queue:dead-letter --retry-all`.
Повторная доставка безопасна — уже отправленное обработчик считает дублем.

`broadcast:status` показывает рассылки и сверяет их счётчики с журналом доставок. Кампания,
висящая в `sending` дольше получаса, до конца не дошла: сначала посмотрите
`queue:dead-letter` — если задача жива, её лучше вернуть в работу. Если возвращать нечего,
закрыть строку по реальным данным журнала:

```bash
corepack pnpm broadcast:status --close <id рассылки>
```

Команда откажется закрывать кампанию, задача которой ещё в очереди: иначе счётчики разойдутся
с тем, что на самом деле уходит людям.

Цены правит `price:set`, а не ручной SQL:

```bash
corepack pnpm price:set --product adult_standard --min 1 --rub 12          # примерка
corepack pnpm price:set --product adult_standard --min 1 --rub 12 --apply  # запись
```

Он меняет ровно одно правило и откажется работать, если под условие подходит больше одного.
Голый `update` по `pricing_rules` опасен: без `where` он ставит цену всем тарифам сразу,
включая VIP и семейные, а продажи в этот момент идут.

### Ошибки, которые уже случались

- `Killed` при установке зависимостей — кончилась память. Появился swap, но
  если повторится, ставьте с `--network-concurrency=1 --child-concurrency=1`.
- `command not found` при попытке загрузить `.env` через `.` — так и должно
  быть, см. раздел про пересборку панели.
- Задачи в очереди, повторяющиеся с ошибкой, — их текст лежит в базе, логи
  пишут только тип:
  `select name, output->>'message' from pgboss.job where id = '<jobId из лога>';`
- `chat not found` при уведомлении администратора — этот человек не открывал
  бота и не нажимал «Старт». Telegram не позволяет боту писать первым.
