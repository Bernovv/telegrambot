# ADR 0020: Валидированный ввод в сценарии

## Статус

Принято 26 июля 2026 года.

## Контекст

Сценарию продажи нужны ответы пользователя до вызова операций заказа. Telegram доставляет обычный
текст без идентификатора сессии, а повторная доставка update не должна повторять переход.
Произвольный или неоднозначный ввод нельзя сохранять как подтвержденное бизнес-значение.

## Решение

- Публиковать `text_input` и `number_input` только с одним автоматическим переходом без подписи.
- Требовать безопасный `contextKey`: латинский идентификатор длиной до 64 символов.
- Для текста требовать явные `minimumLength` и `maximumLength` в диапазоне 1–4096.
- Для числа принимать только каноническое безопасное целое и требовать явные целые `minimum` и
  `maximum`.
- Находить ожидающую сессию по владельцу Telegram и блокировать её строку в транзакции.
- При нескольких подходящих сессиях не угадывать цель и не изменять ни одну из них.
- Сохранять типизированное значение в `scenario_sessions.context` атомарно с переходом и
  optimistic `lock_version`.
- Использовать idempotency key вида `telegram_update:<updateId>:scenario_input`.
- Не записывать исходный ответ в `scenario_events` и `last_input`; trace содержит только тип
  команды, результат проверки и метаданные ключа.

## Последствия

- Повтор Telegram update не повторяет переход и не перезаписывает контекст.
- Некорректный ответ оставляет сессию на input-узле и получает безопасную подсказку.
- Контекст готов для будущих application-портов заказа, но action-узлы остаются закрытыми до
  отдельных контрактов и тестов.
- Текстовый контекст может содержать персональные данные, поэтому его нельзя выводить в логи,
  Graphify или диагностические дампы.

## Совместимость и откат

Новая миграция не требуется: используется существующий JSONB `scenario_sessions.context` и
append-only `scenario_events`. Откат приложения прекращает обработку input-узлов, не изменяя и не
удаляя сохраненные сессии.
