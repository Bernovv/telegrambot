# ADR 0032: Неизменяемые снимки аудитории сегмента

## Контекст

Опубликованная версия сегмента фиксирует правило отбора, но состав пользователей меняется со
временем. Для юридически или финансово значимой рассылки необходимо сохранить конкретных
получателей до начала отправки. Материализация большой аудитории внутри HTTP-запроса создаёт
риск таймаута и нагрузки на API.

## Решение

- Администратор с правом `broadcasts.send` создаёт audited-заявку для точной опубликованной
  версии сегмента.
- HTTP-запрос только создаёт состояние `pending`. Состав аудитории материализует отдельный
  worker с ограниченным размером пакета и интервалом опроса.
- Worker блокирует ожидающие заявки через `FOR UPDATE SKIP LOCKED`, строит только
  параметризованный предикат и выполняет один `INSERT ... SELECT`.
- В таблице участников сохраняются `snapshot_id`, внутренний `user_id` и время фиксации.
  Профиль пользователя не копируется: членство неизменяемо, а административный sample показывает
  текущие маскированные данные.
- Заполнение участников, перевод снимка в `ready` и событие
  `SegmentAudienceSnapshotReady` в transactional outbox выполняются одной транзакцией.
- При ошибке транзакция откатывается, заявка остаётся `pending` и может быть безопасно повторена.
- Для одной версии одновременно существует не более одной ожидающей заявки. После готовности
  можно создать новый снимок той же версии в другой момент времени.
- PostgreSQL-триггеры запрещают изменение и удаление готового снимка, а участники являются
  append-only.

## Последствия

- Рассылка сможет ссылаться на точный `snapshot_id`, не пересчитывая аудиторию.
- Состав снимка не меняется при последующих изменениях статусов, категорий или профиля.
- Сам контент рассылки, расписание и delivery ledger этим этапом не создаются.

## Совместимость

Миграция `20260729160000_segment_audience_snapshots` только добавляет таблицы, индексы и защитные
триггеры. Существующие сегменты, preview и пользовательские назначения не изменяются.
