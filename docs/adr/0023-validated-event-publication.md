# ADR 0023: Атомарная публикация подготовленного мероприятия

## Статус

Принято.

## Контекст

Заказ разрешен только для мероприятия в статусе `published`. Ранее администратор мог подготовить
общие данные, продукты, цены, оферту и сценарий, но не мог открыть продажи без ручного изменения
БД. Простое обновление статуса опасно: между проверкой каталога и записью публикации другой
администратор мог изменить агрегат.

## Решение

- `POST /api/v1/events/:id/publish` требует отдельное разрешение `events.publish`, причину и точный
  `expectedLockVersion`.
- Application service не обращается к таблицам напрямую и делегирует одну атомарную операцию
  репозиторию мероприятия.
- PostgreSQL-адаптер берет advisory lock `event-sales:<eventId>`, блокирует строку мероприятия и
  проверяет статус `draft` и оптимистическую версию.
- Публикация требует название, дату, контакт поддержки, хотя бы один активный продукт, активную
  положительную активную цену для каждого активного продукта, опубликованный сценарий и активную
  оферту, если она обязательна. Нулевая цена закрыта до реализации бесплатного заказа.
- Проверка дочерних записей, изменение `status`, заполнение `published_at`, увеличение
  `lock_version` и добавление `event.published` в `audit_log` выполняются в одной транзакции.
- BFF разрешает только точный путь публикации того же источника. Карточка мероприятия показывает
  готовность каждого требования и не отправляет заведомо неполный запрос.

## Последствия

- Полный путь подготовки мероприятия больше не требует ручного SQL.
- После публикации существующие draft-only операции возвращают конфликт и интерфейс становится
  доступным только для чтения.
- Конкурентное изменение приводит к `ADMIN_EVENT_VERSION_CONFLICT`, а неполный каталог к
  `ADMIN_EVENT_PUBLICATION_REQUIREMENTS_FAILED` со стабильным списком причин.
- Уже созданные заказы не меняются, так как публикация не затрагивает их снимки.

## Откат

Новая миграция не требуется. API, BFF и кнопку можно откатить без изменения схемы. Уже
опубликованные мероприятия не переводятся обратно автоматически; изменение их жизненного цикла
должно выполняться отдельной проверенной операцией, а не ручным SQL.
