# ADR 0024: Обязательный TOTP MFA для веб-админки

## Статус

Принято.

## Контекст

API уже проверяет claim `aal` и требует `aal2` для MFA-ролей и чувствительных разрешений, но
веб-интерфейс умел только вход по email и паролю. Первый `super_admin` поэтому получал сессию
`aal1` и не мог использовать защищенные маршруты. Ослабление роли или backend-проверки нарушило
бы модель безопасности.

## Решение

- После успешного пароля интерфейс переводит администратора на `/mfa`.
- Если у пользователя нет подтвержденного TOTP-фактора, Supabase Auth создает enrollment.
  Браузер показывает QR-код и резервный секрет, не отправляя их в Nest API и не записывая в логи.
- Незавершенный старый TOTP enrollment удаляется только при явном повторном запуске настройки.
- Подтверждение выполняется `challengeAndVerify`; успешный ответ обновляет сессию и JWT до `aal2`.
- Серверный layout всех административных страниц повторно проверяет пользователя и текущий AAL.
  Сессия ниже `aal2` перенаправляется на `/mfa`.
- QR SVG передается как percent-encoded data URL в компонент изображения, а не вставляется в DOM
  как исполняемая разметка.

## Последствия

- Веб-админка требует MFA для всех ролей, что строже минимальной backend-политики.
- Финансовые и системные маршруты продолжают независимо проверять `aal2` в API.
- Потерянный фактор восстанавливается только через подтвержденную административную операцию
  Supabase Auth; приложение не предоставляет обход или резервный одноразовый код.
- Секрет enrollment существует только в состоянии браузера до завершения настройки или обновления
  страницы.

## Откат

Миграция БД не требуется. UI можно откатить, но backend продолжит запрещать MFA-роли и
чувствительные операции для `aal1`. Откат серверной проверки всех страниц не должен сопровождаться
ослаблением API.
