# Аккаунт компании в Telegram: подключение и проверка

Фаза 2 плана `План_интеграции_каналов.md`. Канал — не бот, а обычный аккаунт на
корпоративном номере, который живёт на сервере по MTProto. Приложения с этим аккаунтом у
менеджеров нет, поэтому «разговаривать только через панель» здесь не договорённость, а
единственный вход: другого не существует.

Сделано на сегодня: настройки, вход по коду и проверка состояния. Приёма входящих и отправки
из панели по этому каналу **ещё нет** — они следующим шагом, и до них аккаунт просто сидит
авторизованным.

## Почему не Cloudflare, как у бота

Бот ходит в Telegram через воркер из `TELEGRAM_API_ROOT`: Bot API — это обычные
HTTPS-запросы, и воркер их перекладывает. Аккаунт живёт по MTProto — бинарный протокол
поверх сырого TCP с постоянным соединением. У Cloudflare Worker входа для TCP нет, и тот же
приём здесь не работает. Отсюда отдельный прокси на зарубежной машине: SOCKS5 либо MTProxy.

Прокси обязателен на продакшне: без `TELEGRAM_ACCOUNT_PROXY` приложение с `APP_ENV=production`
не поднимется вовсе. Это сделано намеренно — молча пойти напрямую значит повторить 27 июля,
когда затёртый адрес прокси не уронил ничего, а просто на два часа выключил доставку.

## Что нужно завести один раз

1. **Зарубежная VPS с SOCKS5.** Минимальный тариф, постоянный IP. Прокси закрыть паролем
   **и** файрволом на адрес нашего сервера: открытый прокси находят сканерами за сутки, и
   ходить через него начинают чужие — с нашего адреса.
2. **`api_id` и `api_hash`** — `my.telegram.org` под тем же корпоративным номером, раздел
   API development tools. Сайт из РФ обычно требует VPN.
3. **Облачный пароль (двухфакторная защита) на аккаунте.** Без него аккаунт угоняется одним
   перехваченным кодом, а через этот аккаунт идёт вся переписка с клиентами.
4. **Профиль**: имя, аватар, описание — до первого сообщения клиенту. Пустой профиль,
   который пишет незнакомым, читается как спам и собирает жалобы.
5. **Каталог сессии** на сервере, доступный только пользователю процесса:

   ```bash
   install -d -m 700 -o root -g root /var/lib/telegrambot/tg-account
   ```

## Настройки в `.env`

```
TELEGRAM_ACCOUNT_API_ID=1234567
TELEGRAM_ACCOUNT_API_HASH=…
TELEGRAM_ACCOUNT_PHONE=+7XXXXXXXXXX
TELEGRAM_ACCOUNT_SESSION_DIR=/var/lib/telegrambot/tg-account
TELEGRAM_ACCOUNT_DB_KEY=…            # openssl rand -hex 32
TELEGRAM_ACCOUNT_PROXY=socks5://логин:пароль@хост:порт
TELEGRAM_ACCOUNT_DEVICE_MODEL=Business Proriv CRM
```

Спецсимволы в пароле прокси — процентами: `@` это `%40`, `#` это `%23`. Иначе адрес
разберётся не так, и разберётся молча.

Проверить заполненность: `pnpm env:check`. Пока `TELEGRAM_ACCOUNT_API_ID` пуст, канал
выключен целиком и проверка про него молчит.

## Вход

Запускать **на сервере**, а не с ноутбука. Telegram смотрит, откуда вошли: вход из Москвы с
последующей работой из Амстердама — это ровно та смена места, из-за которой аккаунт просят
подтвердить себя, а в плохом случае блокируют. Один адрес на вход и на работу.

```bash
cd ~/telegrambot && pnpm account:login
```

Скрипт сам подставит номер из `.env`. У вас спросят код подтверждения — он придёт в
приложение Telegram на этом номере, а если живых сессий нет, то по SMS, — и облачный пароль.
Пароль вводится без эха: скрипт запускают по ssh, и напечатанный пароль остался бы на экране
до конца дня.

После входа скрипт сверяет номер: вошли не под тем — скажет об этом и не сделает вид, что
всё хорошо. Перепутанный номер это не опечатка в конфиге, а разговор клиента с посторонним
аккаунтом.

## Проверка

```bash
cd ~/telegrambot && pnpm account:status
```

Показывает состояние авторизации, прокси и — главное — состояние соединения. Это
единственный честный ответ на вопрос «канал живой?»: об ошибках прокси TDLib не сообщает, а
молча пробует соединиться снова, и снаружи это выглядит как тишина. Тишина бывает двух
видов — никто не писал и мы отрезаны от Telegram, — и различить их можно только так.

Не дождались `ready` — проверьте прокси с этого же сервера:

```bash
curl -x socks5h://логин:пароль@хост:порт https://api.telegram.org
```

## Сессия

У TDLib нет строки сессии: **авторизация — это каталог** `TELEGRAM_ACCOUNT_SESSION_DIR`.
Отсюда три следствия:

- каталог обязан попадать в резервную копию — потеря означает новый вход по коду;
- каталог не переносится в репозиторий и не копируется на другие машины «на всякий случай»:
  две копии на одной сессии Telegram считает двумя устройствами и начинает рвать соединение
  по кругу;
- при переезде сервера каталог переезжает целиком, и повторный вход не нужен.

Список прокси TDLib тоже живёт в этом каталоге и переживает перезапуски. Поэтому при каждом
старте он приводится к `.env`: что записано в настройках, то включено, лишнее удаляется.
Единственный источник правды — `.env`, а не память TDLib.

## Выход и смена номера

```bash
cd ~/telegrambot && pnpm account:login --forget
```

Спросит подтверждение, завершит сессию на стороне Telegram и удалит каталог. Порядок важен и
он именно такой: удалить каталог, не выйдя, значит оставить в списке устройств аккаунта вход,
который уже некому завершить. История диалогов при этом остаётся — она в нашей базе, а не в
каталоге TDLib.

## Если аккаунт заблокировали

План на этот случай в `План_интеграции_каналов.md`, раздел 2.2: резервный номер, переход на
Business API для ответов и звонок как первое касание. Переписка от бана не страдает — она
у нас.
