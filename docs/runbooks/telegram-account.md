# Аккаунт компании в Telegram: подключение и проверка

Фаза 2 плана `План_интеграции_каналов.md`. Канал — не бот, а обычный аккаунт на
корпоративном номере, который живёт на сервере по MTProto. Приложения с этим аккаунтом у
менеджеров нет, поэтому «разговаривать только через панель» здесь не договорённость, а
единственный вход: другого не существует.

Сделано: настройки, вход по коду, проверка состояния, приём входящих и ответ из панели.

## Почему не Cloudflare, как у бота

Бот ходит в Telegram через воркер из `TELEGRAM_API_ROOT`: Bot API — это обычные
HTTPS-запросы, и воркер их перекладывает. Аккаунт живёт по MTProto — бинарный протокол
поверх сырого TCP с постоянным соединением. У Cloudflare Worker входа для TCP нет, и тот же
приём здесь не работает. Отсюда отдельный прокси на зарубежной машине: SOCKS5 либо MTProxy.

Прокси обязателен на продакшне: без `TELEGRAM_ACCOUNT_PROXY` приложение с `APP_ENV=production`
не поднимется вовсе. Это сделано намеренно — молча пойти напрямую значит повторить 27 июля,
когда затёртый адрес прокси не уронил ничего, а просто на два часа выключил доставку.

## Что нужно завести один раз

1. **Зарубежная VPS с SOCKS5.** Минимальный тариф, постоянный IP. Прокси закрыть паролем
   **и** файрволом на адрес нашего сервера: открытый прокси находят сканерами за сутки, и
   ходить через него начинают чужие — с нашего адреса.
2. **`api_id` и `api_hash`** — `my.telegram.org` под тем же корпоративным номером, раздел
   API development tools. Сайт из РФ обычно требует VPN.
3. **Облачный пароль (двухфакторная защита) на аккаунте.** Без него аккаунт угоняется одним
   перехваченным кодом, а через этот аккаунт идёт вся переписка с клиентами.
4. **Профиль**: имя, аватар, описание — до первого сообщения клиенту. Пустой профиль,
   который пишет незнакомым, читается как спам и собирает жалобы.
5. **Каталог сессии** на сервере, доступный только пользователю процесса:

   ```bash
   install -d -m 700 -o root -g root /var/lib/telegrambot/tg-account
   ```

## Настройки в `.env`

```
TELEGRAM_ACCOUNT_API_ID=1234567
TELEGRAM_ACCOUNT_API_HASH=…
TELEGRAM_ACCOUNT_PHONE=+7XXXXXXXXXX
TELEGRAM_ACCOUNT_SESSION_DIR=/var/lib/telegrambot/tg-account
TELEGRAM_ACCOUNT_DB_KEY=…            # openssl rand -hex 32
TELEGRAM_ACCOUNT_PROXY=socks5://логин:пароль@хост:порт
TELEGRAM_ACCOUNT_DEVICE_MODEL=Business Proriv CRM
```

Спецсимволы в пароле прокси — процентами: `@` это `%40`, `#` это `%23`. Иначе адрес
разберётся не так, и разберётся молча.

Схему можно писать и как `socks5h://` — так её пишут в проверочной команде curl, и
оттуда строку обычно и копируют. Для нас разницы нет: буква `h` у curl означает «резолвить
имена через прокси», а TDLib и так ходит через него целиком.

Проверить заполненность: `pnpm env:check`. Пока `TELEGRAM_ACCOUNT_API_ID` пуст, канал
выключен целиком и проверка про него молчит.

## Вход

Запускать **на сервере**, а не с ноутбука. Telegram смотрит, откуда вошли: вход из Москвы с
последующей работой из Амстердама — это ровно та смена места, из-за которой аккаунт просят
подтвердить себя, а в плохом случае блокируют. Один адрес на вход и на работу.

```bash
cd ~/telegrambot && pnpm account:login
```

Скрипт сам подставит номер из `.env`. У вас спросят код подтверждения — он придёт в
приложение Telegram на этом номере, а если живых сессий нет, то по SMS, — и облачный пароль.
Пароль вводится без эха: скрипт запускают по ssh, и напечатанный пароль остался бы на экране
до конца дня.

После входа скрипт сверяет номер: вошли не под тем — скажет об этом и не сделает вид, что
всё хорошо. Перепутанный номер это не опечатка в конфиге, а разговор клиента с посторонним
аккаунтом.

## Проверка

```bash
cd ~/telegrambot && pnpm account:status
```

Показывает состояние авторизации, прокси и — главное — состояние соединения. Это
единственный честный ответ на вопрос «канал живой?»: об ошибках прокси TDLib не сообщает, а
молча пробует соединиться снова, и снаружи это выглядит как тишина. Тишина бывает двух
видов — никто не писал и мы отрезаны от Telegram, — и различить их можно только так.

Не дождались `ready` — проверьте прокси с этого же сервера:

```bash
curl -x socks5h://логин:пароль@хост:порт https://api.telegram.org
```

## Процесс приёма

Входящие принимает отдельный процесс `tg-account` в pm2, рядом с ботом, но независимо от
него. Отдельный он не из аккуратности: бот продаёт билеты, и его падение стоит денег, а
аккаунт держит постоянное соединение через прокси за границей — поводов упасть у него
вдвое больше, и делить с ним судьбу продаже билетов незачем.

```bash
pm2 start deploy/run-tg-account.sh --name tg-account --cwd ~/telegrambot
pm2 save
```

**Экземпляр должен быть ровно один.** Вторая копия на той же сессии для Telegram — это
второе устройство, и соединение начинает рваться по кругу. Снаружи это выглядит как «канал
моргает»; причина обычно в том, что кто-то оставил запущенным `pnpm account:status` или
второй процесс.

Что пишется в ленту:

| Что прислали | Что в ленте |
|---|---|
| текст | текст |
| фотография, видео, кружок, гифка | подпись + вложение, файл скачивается к нам |
| голосовое | вложение, слушается плеером в панели |
| документ | имя файла + вложение |
| стикер | эмодзи стикера |
| контакт, геометка | строка с пометкой вида |
| что-то незнакомое | строка без текста, само обновление целиком — в `payload` |

Групповые чаты и наши собственные исходящие в ленту не идут: первое — чужой разговор,
второе пишется в момент отправки.

**Правки сообщений пока не разбираются.** У бота они приходят отдельным понятным
обновлением, а у TDLib то же обновление срабатывает и без правки — например, когда Telegram
сам подтягивает к ссылке предпросмотр. Отличать одно от другого нужно отдельно, а не заодно;
до тех пор в ленте остаётся исходный текст.

### Ответ из панели

Ответ уходит той же очередью, что у бота, но **очередь отобрана по транспорту**: ответ,
написанный в ветку аккаунта, отправляет процесс `tg-account`, а ответ в ветку бота — воркер.
Без этого отбора ответ уходил бы от бота — то есть человек получал бы его от другого
собеседника, чем тот, с которым разговаривал. Так и случилось при первой проверке.

В панели ветки различаются подписью: «Telegram · бот» и «Telegram · аккаунт». Подпись
появляется только тогда, когда в одном мессенджере есть обе, — там, где ветка одна, лишнее
слово мешает.

**Отправленным считается только подтверждённое.** TDLib отвечает на отправку сразу, ещё до
того как сообщение ушло: он возвращает заготовку с временным номером и берётся доставить её
сам, а настоящая судьба приходит позже отдельным обновлением. Поверить первому ответу
значило бы записывать «доставлено» тому, что не дошло: человек закрылся настройками
приватности, номер в чёрном списке, сообщение отвергнуто как спам. Поэтому отправка ждёт
подтверждения до минуты, а не дождавшись — возвращает реплику в очередь.

Файлы отправляются: фотография уходит фотографией, остальное документом. Геометку и контакт
панель отправить не даст — их и не из чего собрать.

### Поиск человека по номеру телефона

Написать первым в Telegram можно только тому, чей идентификатор известен, а у большинства
людей в базе есть телефон и нет ника. Узнать, есть ли у номера аккаунт, умеет только живой
клиент — ни Bot API, ни какая-либо другая открытая ручка по номеру никого не находит.
Менеджеры делали это руками: отправляли номер себе в чат, зажимали его и смотрели,
предложит ли Telegram написать. Кнопка «Найти по номеру» в карточке человека делает ровно
то же самое, вызовом `searchUserByPhoneNumber`.

Между кнопкой и вызовом стоит очередь `contact_channel_lookups` — **общая на три
мессенджера**, и каждый процесс берёт из неё только свои строки: спросить Telegram может
лишь тот, у кого сессия Telegram. Панель кладёт просьбу и перечитывает карточку раз в три
секунды, не дольше минуты. Подробности про очередь целиком — в `docs/runbooks/channel-lookups.md`.

**Найдя человека, процесс тут же заводит ему ветку переписки** — `telegram` · `account`, в
одной транзакции с записью ответа. Без неё найденный идентификатор был бы числом в базе, а
менеджеру нужно поле ввода. Если человек когда-то писал аккаунту сам, а карточку тогда не
опознали, ветка не создаётся заново: она достраивается, и вся прошлая история приезжает в
карточку.

Исходов три, и один честно называет две причины сразу:

| Что показывает панель | Что это значит |
|---|---|
| нашли — можно писать | идентификатор есть, ветка заведена |
| Telegram не нашёл этот номер | либо аккаунта нет, либо человек закрылся настройкой «кто может найти меня по номеру» |
| до Telegram не дозвонились | прокси, лимит, обрыв — про человека это не говорит ничего |

Различить два случая во второй строке **нельзя**: Telegram отвечает на них одинаково
нарочно, иначе по ответам можно было бы перебирать номера и составлять список тех, у кого
аккаунт есть. Выбирать одну из двух причин наугад значило бы врать менеджеру про человека.

**С 26.08.2026 строка появляется не только по кнопке**, но и сама — на каждого нового
человека с телефоном (решение владельца от 23.08.2026). Осторожность от этого стала важнее,
а не меньше: пачка в три запроса за проход, пауза пятнадцать секунд, потолок в полтораста
проверок на канал в сутки. Перебор чужих номеров Telegram считает разведкой и отвечает
сначала задержками, а потом запретом писать незнакомым — на том самом аккаунте, через
который идёт вся переписка с клиентами. При лимите ждём срок, который Telegram назвал сам:
попытка раньше времени продлевает запрет.

Настройки — `TELEGRAM_PHONE_LOOKUP_BATCH_SIZE`, `_POLL_INTERVAL_MS`, `_PAUSE_MS`,
`_MAX_ATTEMPTS`, `_RETRY_DELAY_MS`. В `.env` их можно не заводить: значения по умолчанию
рабочие и намеренно осторожные.

Уже найденного повторно не ищем — незачем тратить запрос. Исключение: телефон в карточке
поправили, и прежний ответ относится к другому человеку; карточка это видит и предлагает
искать заново.

### Вложения

Файлы аккаунта забирает **он сам**, а не воркер. Причина в том, как устроен TDLib:
идентификатор файла у него — число, живущее внутри сессии, а не строка Bot API, по которой
можно постучаться со стороны. Поэтому очередь скачивания разделена по транспорту: воркер
берёт вложения бота, `tg-account` — свои. Общая очередь означала бы, что воркер честно
пробует скачать файл аккаунта пять раз, каждый раз мимо, и через час помечает его
несбывшимся — а файл при этом жив.

Папка та же, что у бота: `CONVERSATION_FILES_DIR`, раскладка по годам и месяцам. Сколько
ушло места — `pnpm conversations:files`.

Скачанное TDLib удаляет из своего кэша после того, как файл лёг к нам: иначе каждое
голосовое лежало бы на диске дважды.

## Сессия

У TDLib нет строки сессии: **авторизация — это каталог** `TELEGRAM_ACCOUNT_SESSION_DIR`.
Отсюда три следствия:

- каталог обязан попадать в резервную копию — потеря означает новый вход по коду;
- каталог не переносится в репозиторий и не копируется на другие машины «на всякий случай»:
  две копии на одной сессии Telegram считает двумя устройствами и начинает рвать соединение
  по кругу;
- при переезде сервера каталог переезжает целиком, и повторный вход не нужен.

Список прокси TDLib тоже живёт в этом каталоге и переживает перезапуски. Поэтому при каждом
старте он приводится к `.env`: что записано в настройках, то включено, лишнее удаляется.
Единственный источник правды — `.env`, а не память TDLib.

## Выход и смена номера

```bash
cd ~/telegrambot && pnpm account:login --forget
```

Спросит подтверждение, завершит сессию на стороне Telegram и удалит каталог. Порядок важен и
он именно такой: удалить каталог, не выйдя, значит оставить в списке устройств аккаунта вход,
который уже некому завершить. История диалогов при этом остаётся — она в нашей базе, а не в
каталоге TDLib.

## Если аккаунт заблокировали

План на этот случай в `План_интеграции_каналов.md`, раздел 2.2: резервный номер, переход на
Business API для ответов и звонок как первое касание. Переписка от бана не страдает — она
у нас.
