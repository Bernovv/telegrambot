# Переписка: что записывается, где лежит и что делать, когда не доехало

Фаза 1 плана `План_интеграции_каналов.md`. До неё входящий текст жил ровно столько, сколько
его разбирал сценарий: вопрос, заданный не в тот момент, не оставлял ни строки.

## Что записывается

| Откуда | Что | Где стоит хук |
|---|---|---|
| Telegram, входящее | любое сообщение, включая голосовые и фото, которых бот не понимает | middleware до всех обработчиков |
| Telegram, исходящее | всё, что бот сказал | преобразователь запросов к api |
| MAX, входящее | любое обновление с сообщением, включая незнакомые типы | начало разбора |
| MAX, исходящее | всё, что бот сказал | единственное место отправки |
| Воркер | билеты, напоминания, продолжения сценария, рассылки | обёртка на общий порт отправки |

Не записывается: групповые чаты и уведомления организаторам
(`ADMIN_NOTIFICATION_TELEGRAM_CHAT_ID`). Первое — чужой разговор, второе — сообщение самим
себе.

Таблицы: `conversations` (диалог), `conversation_messages` (реплики), `conversation_attachments`
(вложения). Все три только на добавление; правка клиента — новая строка со ссылкой на
исходную.

## Как это видно в панели

Пока — строкой в ленте касаний карточки: «Telegram · Человек» и выдержка в 200 знаков.
Очередь сообщений подряд слипается в одно касание за полчаса, иначе лента касаний стала бы
той же перепиской без текста. Ответ бота касанием не считается.

Полное окно диалога с историей и полем ответа — фаза 4.

## Вложения

Файлы храним у себя. Решение владельца от 23.08.2026: **пока вечно**, и смотрим за расходом
места. Причина не в аккуратности: путь к файлу у Telegram живёт около часа, идентификатор —
не вечно, и через год половина вложений оказалась бы недоступной.

Скачивание — отдельный проход воркера, а не часть приёма: приём отвечает мессенджеру, и
тянуть в этот момент файл из чужой сети значит менять целость переписки на скорость ответа.

### Включение

```bash
mkdir -p /var/lib/telegrambot/conversation-files
chown -R root:root /var/lib/telegrambot/conversation-files
```

В `.env`: `CONVERSATION_FILES_DIR=/var/lib/telegrambot/conversation-files`. Пусто — проход не
поднимается вовсе, и в базе остаются только метаданные. Это безопасное состояние, но
недолгое: через год такие вложения не забрать.

Остальные настройки со значениями по умолчанию описаны в `.env.example`. Менять стоит разве
что `CONVERSATION_FILES_POLL_INTERVAL_MS` (по умолчанию пять минут: вложение нужно к тому
моменту, когда менеджер откроет диалог, а не сию секунду).

### Сколько места ушло

```bash
pnpm conversations:files
```

Показывает по месяцам количество и объём скачанного, состояния очереди и то, что не
скачалось, — с причиной. Рядом печатает команду `du -sh` для настоящей папки: расхождение с
базой означает, что файлы удаляли руками.

### Что делать со строками `failed`

`failed` означает: пробовали столько раз, сколько договорились (`CONVERSATION_FILES_MAX_ATTEMPTS`,
по умолчанию пять, с удвоением паузы), и хватит. Причина видна в `failure_reason` и в выводе
`pnpm conversations:files`.

Частые причины:

- **«канал не отдаёт этот файл»** — у Telegram истёк путь либо файла у него больше нет.
  Вернуть нельзя; если файл нужен, его просят прислать заново.
- **«нет загрузчика для канала»** — канал MAX включён, а уведомления Telegram выключены или
  наоборот. Это наша ненастроенность, а не сбой: почините окружение и верните строки в
  очередь.
- **«файл больше предела»** — прислали больше `CONVERSATION_FILES_MAX_BYTES`.

Вернуть выбранные вложения в очередь:

```sql
update public.conversation_attachments
   set download_status = 'pending', failure_reason = null,
       download_attempts = 0, next_attempt_at = null
 where id = '<id>';
```

Это безопасно: строка вернётся в очередь и будет скачана обычным проходом. Массово так делать
не стоит — если причина не устранена, все пять попыток повторятся впустую.

## Если запись переписки не работает

Она **не может** уронить разговор: служба записи не бросает исключений, а сообщает о неудаче
в журнал и возвращает `null`. Значит, симптом всегда один — в базе не появляются строки,
а бот при этом отвечает как обычно.

```bash
pm2 logs api --lines 200 | grep "conversation message not recorded"
```

```sql
select channel, transport, status, last_inbound_at
  from public.conversations
 order by last_inbound_at desc nulls last
 limit 10;
```

Диалоги без карточки — норма, а не поломка: у человека в Telegram может не быть ни ника, ни
телефона, а карточка без единого опознавателя не заводится. Такой диалог привяжется сам,
когда появится ник или телефон.

```sql
select count(*) from public.conversations where contact_id is null;
```
