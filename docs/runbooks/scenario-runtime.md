# Пользовательский runtime сценария

## Область

Runtime включен в long polling и Telegram webhook. Он выполняет опубликованные узлы `start`,
`message`, `menu`, `choice`, `text_input`, `number_input`, `order_start`, `order_add_item`,
`order_summary`, `offer_acceptance`, `payment_start`, `wallet_credit`, `set_status`,
`add_category` и `end`. Остальные action-узлы закрыты до появления отдельных проверенных
application-портов.

## Перед включением

1. Применить `20260726120000_scenario_versions`.
2. Применить `20260726160000_scenario_runtime`.
3. Убедиться, что у мероприятия назначена опубликованная версия.
4. Проверить, что сценарий содержит один `start`, хотя бы один `end`, текст presentation-узлов и
   подписи всех кнопок `menu`/`choice`.
5. Для каждого `text_input` задать `contextKey`, `minimumLength` и `maximumLength`; для
   `number_input` — `contextKey`, целые `minimum` и `maximum`. У input-узла должен быть один
   автоматический переход без подписи.
6. Для прежнего атомарного варианта `order_start` задать валюту и от 1 до 20 уникальных
   `productId` с `quantityContextKey`. Каждый ключ должен ссылаться на ранее сохраненное целое
   положительное количество. Необязательную позицию можно пометить `optional: true`;
   отсутствующее или нулевое количество такой позиции будет пропущено.
7. Для последовательного состава задать `order_start` с `currency` и `mode: "compose"`, после
   него расположить хотя бы один `order_add_item` с `productId`, `quantityContextKey` и
   необязательным `optional`, затем пустой payload `{}` узла `order_summary`. В черновике
   допускается не более 20 уникальных товаров. `walletMode: "all"` применяет доступный внутренний
   баланс, `walletMode: "none"` его не резервирует; при отсутствии поля действует `none`.
8. Расположить legacy `order_start` либо `order_summary` перед `offer_acceptance`, а
   `offer_acceptance` перед `payment_start` на каждом пути. У всех action-узлов заказа должен
   быть один автоматический переход.
9. Для `wallet_credit` задать строку целых копеек `amountKopecks` от `1` до `1000000`,
   трёхбуквенную валюту, причину от 3 до 200 символов и `idempotencyKeyTemplate` из 3–60
   безопасных ASCII-символов. Узел должен иметь один автоматический переход. Bucket всегда
   `bonus`; произвольный cash-equivalent через сценарий запрещён.
10. Для `set_status` задать активный `statusCode` и причину, для `add_category` — активный
    `categoryCode` и причину. Каждый узел должен иметь один автоматический переход. Применить
    `20260728200000_user_statuses_categories`; публикация проверит ссылки на каталог.
11. Убедиться, что активный продукт имеет действующий тариф, продажи открыты, остатка достаточно,
   а для обязательной оферты опубликована активная неизменяемая версия с HTTPS-адресом.
12. Задать общий для API и Telegram-бота `ORDER_TOKEN_SECRET` длиной не менее 32 символов.
   В production локальное значение по умолчанию запрещено.
13. Включить Telegram consumer worker-а: `TELEGRAM_NOTIFICATIONS_ENABLED=true`, тот же
   `TELEGRAM_BOT_TOKEN`, `ORDER_TOKEN_SECRET` и корректный `ADMIN_NOTIFICATION_TELEGRAM_CHAT_ID`.
   Без consumer очередь сохранит события, но не доставит билеты и продолжение сценария.
14. Проверить `/start event_<slug>` в staging для выбранного мероприятия.
15. Опубликовать второе тестовое мероприятие и проверить обычный `/start`: бот должен показать
   карточки ближайших мероприятий с датой, местом, минимальной ценой и кнопкой открытия.
16. Проверить допустимый и недопустимый ответ, повтор одного update и повторное нажатие старой
   кнопки.

## Нормальное поведение

- `/start` закрепляет сессию за точной опубликованной версией.
- Если без deep-link доступно несколько мероприятий, бот выбирает не сам: он показывает не более
  десяти ближайших карточек. Callback содержит только UUID мероприятия, а пользователь повторно
  определяется по `messenger_identities`; чужое или устаревшее сообщение не дает доступ к чужой
  сессии.
- Повторный `/start` продолжает открытую сессию этого мероприятия.
- Новая публикация не переводит уже начатую сессию на другую версию.
- Один Telegram update записывается один раз по idempotency key.
- Callback другого пользователя и callback не из текущего узла не меняют состояние.
- Обычное текстовое сообщение обрабатывается только при единственной принадлежащей пользователю
  сессии, ожидающей `text_input` или `number_input`.
- Допустимый ответ сохраняется в `scenario_sessions.context` в одной транзакции с переходом.
  Исходный текст ответа не записывается в `scenario_events` или `last_input`.
- Недопустимый ответ оставляет сессию на текущем узле и возвращает сообщение с ограничениями.
- Legacy `order_start` читает только опубликованное отображение
  `productId → quantityContextKey` и сразу создает заказ, поэтому уже опубликованные сценарии
  сохраняют прежнее поведение.
- `order_start` с `mode: "compose"` открывает ограниченный черновик без обращения к БД продаж.
  `order_add_item` добавляет или заменяет количество одного товара; необязательное нулевое
  количество удаляет эту позицию. `order_summary` требует непустой черновик и только тогда
  вызывает общий `CreateOrderService`.
- После создания в контексте остается только безопасная ссылка и снимок сумм, а временный
  черновик очищается. Создание заказа и переход сессии выполняются на одном
  PostgreSQL-соединении.
- Ключ создания заказа стабилен для сессии, узла и версии блокировки. Повтор Telegram update не
  создает второй заказ и не дублирует событие outbox.
- При обязательной оферте бот показывает HTTPS-снимок и callback принятия. После подтверждения
  возобновляется только ожидающая сессия владельца, связанная с точным `orderId`.
- Если неизменяемая внешняя сумма больше нуля, `payment_start` показывает callback инициализации
  Т-Банка; URL оплаты появляется только из существующего owner-bound application use case.
- Если внешняя сумма равна нулю, runtime выполняет идемпотентное внутреннее подтверждение
  `internal_order:<orderId>` в общей транзакции: захватывает резерв баланса при его наличии,
  потребляет места, выпускает билеты, сохраняет историю и продолжает сценарий без Т-Банка.
- `wallet_credit` формирует ключ
  `scenario_credit:<template>:<userId>:<eventId>`, блокирует его и wallet account, создаёт
  `SCENARIO_CREDIT` и credit-entry bucket `bonus`, обновляет cached balance и сохраняет переход
  сессии в одной транзакции. Новая сессия или новая версия с тем же template возвращает
  существующую posted-транзакцию без второго начисления.
- `set_status` и `add_category` используют каталог, блокировку пользователя и неизменяемую
  историю назначений. Повтор активного значения является успешной операцией без изменений;
  статусы заменяются только внутри своей группы, категории не заменяют друг друга. Переход
  сессии и назначение фиксируются в одной транзакции.
- Сценарий не доверяет success redirect. Только `PaymentConfirmed` из проверенного webhook,
  reconciliation или ручного административного подтверждения может продвинуть `payment_start`.
- Consumer блокирует сессию только через оплаченный заказ с тем же пользователем и мероприятием,
  сохраняет статус `paid`, переход и `ScenarioPresentationRequested` в одной транзакции.
- Следующий экран доставляется отдельным заданием через арендованный notification ledger.
  Повтор `PaymentConfirmed`, outbox job или Telegram-ошибка не дублирует переход и уже
  отправленные сообщения.
- При отсутствии опубликованного сценария бот показывает прежнее приветствие.

## Диагностика

- `scenario_sessions.status = 'waiting_input'`: пользователь ожидает кнопку или текстовый ответ.
- `completed`: достигнут `end`.
- `blocked`: проверьте `blocked_reason` и последние `scenario_events`.
- `expired`: срок жизни истек; следующий `/start` создаст новую сессию.
- `unsupported_node`: опубликованный граф дошел до action-узла, который еще не подключен.
- Сообщение о недоступном начислении: проверьте payload закреплённой версии, наличие миграции
  `20260728160000_scenario_wallet_credit`, статус wallet account и ledger-транзакцию по
  idempotency key. Не начисляйте компенсацию ручным SQL.
- Сообщение о недоступном статусе или категории: проверьте активность кода в `/classification`,
  допустимые переходы статуса и миграцию `20260728200000_user_statuses_categories`. Не изменяйте
  историю назначений ручным SQL.
- Сообщение о недоступном составе заказа: проверьте значения `quantityContextKey` и опубликованный
  payload закрепленной версии. Для составного потока также проверьте порядок
  `order_start(mode=compose) → order_add_item → order_summary`.
- Ошибка создания заказа: проверьте окно продаж, активные тарифы, вместимость, активную оферту и
  валюту продукта. Не исправляйте снимок заказа или контекст ручным SQL.
- Сессия осталась на `payment_start` после оплаты: проверьте публикацию `PaymentConfirmed`,
  очередь `outbox-dispatch`, heartbeat worker-а и наличие consumer-а Telegram notifications.
- Сессия завершена, но следующий экран не пришел: найдите `ScenarioPresentationRequested` и
  соответствующую запись `notification_deliveries`; проверяйте lease и `last_error_code`, не
  помечайте запись отправленной вручную.
- `step_limit_exceeded`: найдена слишком длинная автоматическая цепочка или цикл.
- Сообщение о нескольких диалогах: найдено больше одной сессии, ожидающей текст. Не выбирайте
  сессию ручным SQL; попросите пользователя заново открыть нужное мероприятие через `/start`.

Не изменяйте текущий узел, версию или trace ручным SQL. Для исправления графа опубликуйте новую
версию; старые сессии должны оставаться воспроизводимыми.

## Откат приложения

Откат на версию без runtime не требует удаления таблиц. Сессии и события остаются в БД. После
повторного включения runtime сессия продолжится по закрепленной версии. Destructive rollback
таблиц требует отдельного ADR и ручного подтверждения.
