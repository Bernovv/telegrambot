# Пользовательский runtime сценария

## Область

Runtime включен в long polling и Telegram webhook. Он выполняет опубликованные узлы `start`,
`message`, `menu`, `choice`, `text_input`, `number_input`, `order_start`, `offer_acceptance`,
`payment_start` и `end`. Остальные action-узлы закрыты до появления отдельных проверенных
application-портов.

## Перед включением

1. Применить `20260726120000_scenario_versions`.
2. Применить `20260726160000_scenario_runtime`.
3. Убедиться, что у мероприятия назначена опубликованная версия.
4. Проверить, что сценарий содержит один `start`, хотя бы один `end`, текст presentation-узлов и
   подписи всех кнопок `menu`/`choice`.
5. Для каждого `text_input` задать `contextKey`, `minimumLength` и `maximumLength`; для
   `number_input` — `contextKey`, целые `minimum` и `maximum`. У input-узла должен быть один
   автоматический переход без подписи.
6. Для `order_start` задать валюту и от 1 до 20 уникальных `productId` с
   `quantityContextKey`. Каждый ключ должен ссылаться на ранее сохраненное целое положительное
   количество. Необязательную позицию можно пометить `optional: true`; отсутствующее или нулевое
   количество такой позиции будет пропущено.
7. Расположить `order_start` перед `offer_acceptance`, а `offer_acceptance` перед
   `payment_start` на каждом пути. У всех трех узлов должен быть один автоматический переход.
8. Убедиться, что активный продукт имеет действующий тариф, продажи открыты, остатка достаточно,
   а для обязательной оферты опубликована активная неизменяемая версия с HTTPS-адресом.
9. Задать общий для API и Telegram-бота `ORDER_TOKEN_SECRET` длиной не менее 32 символов.
   В production локальное значение по умолчанию запрещено.
10. Включить Telegram consumer worker-а: `TELEGRAM_NOTIFICATIONS_ENABLED=true`, тот же
   `TELEGRAM_BOT_TOKEN`, `ORDER_TOKEN_SECRET` и корректный `ADMIN_NOTIFICATION_TELEGRAM_CHAT_ID`.
   Без consumer очередь сохранит события, но не доставит билеты и продолжение сценария.
11. Проверить `/start event_<slug>` в staging для выбранного мероприятия.
12. Проверить допустимый и недопустимый ответ, повтор одного update и повторное нажатие старой
   кнопки.

## Нормальное поведение

- `/start` закрепляет сессию за точной опубликованной версией.
- Повторный `/start` продолжает открытую сессию этого мероприятия.
- Новая публикация не переводит уже начатую сессию на другую версию.
- Один Telegram update записывается один раз по idempotency key.
- Callback другого пользователя и callback не из текущего узла не меняют состояние.
- Обычное текстовое сообщение обрабатывается только при единственной принадлежащей пользователю
  сессии, ожидающей `text_input` или `number_input`.
- Допустимый ответ сохраняется в `scenario_sessions.context` в одной транзакции с переходом.
  Исходный текст ответа не записывается в `scenario_events` или `last_input`.
- Недопустимый ответ оставляет сессию на текущем узле и возвращает сообщение с ограничениями.
- `order_start` читает только опубликованное отображение `productId → quantityContextKey`, создает
  заказ через общий `CreateOrderService` и сохраняет в контексте только безопасную ссылку и снимок
  сумм. Создание заказа и переход сессии выполняются на одном PostgreSQL-соединении.
- Ключ создания заказа стабилен для сессии, узла и версии блокировки. Повтор Telegram update не
  создает второй заказ и не дублирует событие outbox.
- При обязательной оферте бот показывает HTTPS-снимок и callback принятия. После подтверждения
  возобновляется только ожидающая сессия владельца, связанная с точным `orderId`.
- `payment_start` показывает callback инициализации Т-Банка; URL оплаты появляется только из
  существующего owner-bound application use case.
- Сценарий не доверяет success redirect. Только `PaymentConfirmed` из проверенного webhook,
  reconciliation или ручного административного подтверждения может продвинуть `payment_start`.
- Consumer блокирует сессию только через оплаченный заказ с тем же пользователем и мероприятием,
  сохраняет статус `paid`, переход и `ScenarioPresentationRequested` в одной транзакции.
- Следующий экран доставляется отдельным заданием через арендованный notification ledger.
  Повтор `PaymentConfirmed`, outbox job или Telegram-ошибка не дублирует переход и уже
  отправленные сообщения.
- Runtime пока не применяет внутренний баланс. Бесплатные заказы и заказы без внешней суммы
  требуют отдельного атомарного пути подтверждения и не должны публиковаться как промышленный
  сценарий.
- При отсутствии опубликованного сценария бот показывает прежнее приветствие.

## Диагностика

- `scenario_sessions.status = 'waiting_input'`: пользователь ожидает кнопку или текстовый ответ.
- `completed`: достигнут `end`.
- `blocked`: проверьте `blocked_reason` и последние `scenario_events`.
- `expired`: срок жизни истек; следующий `/start` создаст новую сессию.
- `unsupported_node`: опубликованный граф дошел до action-узла, который еще не подключен.
- Сообщение о недоступном составе заказа: проверьте значения `quantityContextKey` и опубликованный
  payload закрепленной версии.
- Ошибка создания заказа: проверьте окно продаж, активные тарифы, вместимость, активную оферту и
  валюту продукта. Не исправляйте снимок заказа или контекст ручным SQL.
- Сессия осталась на `payment_start` после оплаты: проверьте публикацию `PaymentConfirmed`,
  очередь `outbox-dispatch`, heartbeat worker-а и наличие consumer-а Telegram notifications.
- Сессия завершена, но следующий экран не пришел: найдите `ScenarioPresentationRequested` и
  соответствующую запись `notification_deliveries`; проверяйте lease и `last_error_code`, не
  помечайте запись отправленной вручную.
- `step_limit_exceeded`: найдена слишком длинная автоматическая цепочка или цикл.
- Сообщение о нескольких диалогах: найдено больше одной сессии, ожидающей текст. Не выбирайте
  сессию ручным SQL; попросите пользователя заново открыть нужное мероприятие через `/start`.

Не изменяйте текущий узел, версию или trace ручным SQL. Для исправления графа опубликуйте новую
версию; старые сессии должны оставаться воспроизводимыми.

## Откат приложения

Откат на версию без runtime не требует удаления таблиц. Сессии и события остаются в БД. После
повторного включения runtime сессия продолжится по закрепленной версии. Destructive rollback
таблиц требует отдельного ADR и ручного подтверждения.
