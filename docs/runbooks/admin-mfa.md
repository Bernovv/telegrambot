# MFA администраторов

## Обычный вход

1. Администратор вводит email и пароль на `/login`.
2. Интерфейс переводит сессию `aal1` на `/mfa`.
3. При первом входе администратор подключает TOTP-приложение по QR-коду или резервному секрету.
4. Шестизначный код подтверждает фактор через Supabase Auth и обновляет сессию до `aal2`.
5. Только после этого серверный layout открывает `/users`, `/orders` и `/events`.

Nest API независимо проверяет подпись JWT, issuer, audience, время жизни и claim `aal`. Наличие
cookie в Next.js не заменяет backend-авторизацию.

## Требования

- Supabase Auth включен для выбранного staging или production проекта.
- Используются асимметричные signing keys `ES256` или `RS256`.
- `NEXT_PUBLIC_SUPABASE_URL` и publishable key относятся к тому же issuer, которому доверяет API.
- Время на телефоне администратора синхронизировано.
- QR, TOTP secret, access token и refresh token не записываются в тикеты, логи или репозиторий.

## Сбои

- Неверный код: проверить время устройства и ввести следующий TOTP.
- Незавершенная настройка: повторная кнопка подключения удаляет только незавершенный TOTP-фактор
  текущего пользователя и создает новый.
- Потерянное устройство: уполномоченный оператор удаляет фактор через Supabase Auth после
  проверки личности и аудита вне приложения. После этого пользователь проходит enrollment заново.
- Ошибка получения AAL: завершить сессию, проверить Supabase Auth и issuer, затем войти повторно.

Нельзя изменять `requires_mfa`, подменять claim `aal` или отключать backend-проверку для
восстановления доступа.
