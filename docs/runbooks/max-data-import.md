# Перенос боевых данных MAX

Единственный необратимый шаг объединения. Всё остальное можно откатить перезапуском
процесса; этот — нет.

Скрипт — `packages/database/scripts/max-import.ts`, запуск — `pnpm max:import`.

## Важное про источник: у MAX два хранилища

Postgres завели позже файла, и в него попадает не всё. Заказы, кошельки, партнёрка и оферта
— в базе. А люди, их имена и **телефоны** так и остались в `.data/max-users.json`, из
которого читает старая админка: в боевой базе колонка `users.phone` пуста у всех до одного.

Поэтому переносу нужны оба источника. Без файла телефоны не поедут, а часть людей потеряется
совсем — Postgres-строка появлялась, только когда человек доходил до кошелька или заказа,
и те, кто до покупки не дошёл, живут лишь в файле. Это как раз те, с кем предстоит работать.

Связь между хранилищами одна — `max_user_id`. Путь к файлу передаётся в `MAX_USERS_JSON`;
если его не передать, скрипт об этом скажет отдельной строкой в списке непереносимого.

## Как он устроен

**По умолчанию — сухой прогон.** Скрипт делает всю работу целиком и в конце откатывает
транзакцию. Это не «проверка вхолостую», где половину шагов пропускают: база по-настоящему
проверяет каждый чек-констрейнт, каждый внешний ключ и каждый триггер, а потом всё исчезает.
Прогон, который прошёл, значит, что данные действительно помещаются.

**Повтор ничего не портит.** Идентификаторы целевых строк выводятся из исходных
детерминированно, каждая вставка идёт с `on conflict do nothing`, а заказ, который уже
перенесён, второй раз не трогается вовсе. Прогнать импорт дважды — то же самое, что прогнать
один раз.

**Заказ собирается тем же путём, что живая покупка**: сначала строки состава, потом принятие
оферты, потом переходы статуса по разрешённым ступеням. Обойти запреты схемы было бы можно —
и тогда перенесённый заказ оказался бы в состоянии, в которое настоящий прийти не может.

**Цена берётся из самого заказа MAX, а не из каталога.** Важно, сколько человек заплатил, а
не сколько тариф стоит сегодня: заказ на троих по оптовой цене переносится с той ценой,
которая была в чеке.

## Что переносится

| Из MAX | Куда | Как |
|---|---|---|
| `users` из Postgres **и** из файла | `users` + `messenger_identities` (`channel='max'`) | связь по `max_user_id`; `bot_state` кроме `active` становится «бот заблокирован» |
| телефон и имя из файла | `users`, `user_contacts` | источник `max_contact`, а не `import`: человек нажал кнопку, а не приехал таблицей |
| `wallet_accounts` | `wallet_accounts` + одна проводка `MIGRATION_OPENING_BALANCE` | переносится итог, а не история |
| `referral_relations` | `referral_attributions` | партнёр берётся из самой строки, гадать по коду не нужно |
| `orders` | `orders` + `order_items` | тариф ищется в каталоге по коду, цена — из заказа |
| `offer_documents`, `offer_versions`, `offer_acceptances` | те же таблицы | версии заводятся **неактивными**: активная редакция — та, что показывает панель сегодня |

Чего скрипт не делает намеренно: не переносит проводки кошелька построчно (история остаётся
в старой базе, а смешивать две в одной ленте — получить ленту, которой нельзя верить), не
переносит билеты (в MAX их не было) и **ничего не пишет в исходную базу**.

## Что он откажется переносить

Скрипт не угадывает. Каждый пропуск перечислен в отчёте с причиной:

- **Доплаты** (`is_upsell`). В MAX такой заказ хранит разницу, а не полную цену: состав не
  сходится с суммой, и придумывать недостающую строку нельзя.
- **Заказы, где сумма строки не делится на количество нацело.** Округлить значило бы
  переписать чек.
- **Тариф, которого нет в каталоге.**
- **Телефон, не похожий на номер.** Сколько номеров вообще заполнено в MAX, отчёт печатает
  отдельной строкой: без неё «телефоны» просто отсутствовали бы в списке, и было бы не
  понять, номеров нет или они не разобрались.
- **Удержанные деньги в кошельке** (`cached_held`). Удержание — это незавершённая покупка;
  в общей схеме его держит заказ своей проводкой, и восстановить связь вслепую значит
  выдумать её.
- **Согласия, у которых текста нет нигде** — ни в самом согласии, ни в версии оферты.
  Согласие без документа, с которым согласились, — не согласие. Если текст есть у версии,
  берётся он: версия неизменяема и подписана контрольной суммой, это тот же документ.
- **Согласия по заказам, которые не переехали.** Согласие едет следом за заказом, а не
  впереди него: разберитесь с заказом — переедет и оно.

**Разобрать их руками — часть работы, а не мелочь.** Каждый такой заказ это чьи-то деньги.

## Порядок

**1. Копия боевой базы и прогон на ней.** Настоящая проверка — на копии, а не на пустой базе:
пустая проходит всегда.

```bash
pg_dump "$MAX_DATABASE_URL" > /tmp/max-copy.sql
```

**2. Сухой прогон против боевой общей базы.** Он ничего не пишет, поэтому безопасен.

Строку подключения к базе MAX брать не глазами, а из `.env` самого бота — она там уже есть,
и так пароль не попадёт ни в историю терминала, ни в переписку:

```bash
sudo ls -l /home/maxbot/max-bot/.data/max-users.json
```

```bash
cd ~/telegrambot && MAX_USERS_JSON=/home/maxbot/max-bot/.data/max-users.json MAX_DATABASE_URL="$(sudo grep -m1 '^DATABASE_URL=' /home/maxbot/max-bot/.env | cut -d= -f2-)" pnpm max:import
```

База Timeweb принимает только защищённое подключение, и скрипт по умолчанию так и
подключается — как сам MAX-бот. Для локальной копии без TLS: `MAX_DATABASE_SSL=disable`.

Читать отчёт целиком: сколько переносится, что не переносится и почему, и сходится ли сверка.

**3. Разобрать пропущенное.** По каждому заказу из списка — решение: перенести руками,
оставить в MAX или признать неактуальным. Запускать запись, не разобрав их, нельзя.

**4. Окно обслуживания.** Оба бота остановлены, иначе в MAX появятся новые заказы уже после
снимка:

```bash
systemctl stop max-bot
```

**5. Запись:**

```bash
cd ~/telegrambot && MAX_USERS_JSON=/home/maxbot/max-bot/.data/max-users.json MAX_DATABASE_URL="$(sudo grep -m1 '^DATABASE_URL=' /home/maxbot/max-bot/.env | cut -d= -f2-)" pnpm max:import --apply
```

**6. Сверка после записи.** Отчёт печатает её сам; кроме того:

```sql
select channel, status, count(*), sum(total_kopecks)
  from public.orders group by channel, status order by channel, status;
```

```sql
select count(*) as людей_из_max from public.messenger_identities where channel = 'max';
```

**7. Включить канал MAX** — по `max-channel.md`, и только после этого запускать приём.

## Если что-то пошло не так

Скрипт работает одной транзакцией: сбой на любом шаге откатывает всё. Полупереноса не
бывает — значит, после ошибки можно спокойно разобраться и запустить заново.

Уже записанное откатить нечем, и это причина не торопиться с шагом 5. Страховка одна —
снимок общей базы перед записью:

```bash
pg_dump "$DATABASE_DIRECT_URL" > /tmp/unified-before-max-import.sql
```

## Что проверено

Скрипт прогнан на копии схемы MAX с данными, похожими на боевые: разные тарифы, оптовая
цена, детские билеты, отменённый и скрытый заказы, доплата, заказ с неделимой суммой,
кошельки с удержанием, партнёрские связи и согласия с офертой.

Проверено, что цена переносится из заказа (тройка по 2090 ₽ осталась тройкой по 2090 ₽, а не
стала по 2590 ₽ из каталога), телефоны в трёх разных написаниях нормализуются одинаково,
скрытый заказ приезжает скрытым с объяснением, а **повторный запуск не создаёт ни одной
лишней строки** — на первом прогоне это как раз не работало и было исправлено.

Там же нашлось второе: подтверждённый телефон без времени подтверждения (в MAX так бывает)
схему не проходил. Теперь в этом случае берётся время появления человека — раньше он
подтвердить не мог.
