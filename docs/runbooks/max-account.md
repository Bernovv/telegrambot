# Аккаунт компании в MAX: подключение и проверка

Аккаунт компании в MAX — это **не бот**. Обычный аккаунт на корпоративном номере, который
живёт на сервере и от имени которого менеджеры отвечают из панели. Решение владельца от
23.08.2026: в MAX разговаривает живое имя, а бот остаётся исключительно на продаже билетов —
сценарий, оплата, QR, напоминания.

Зачем вообще аккаунт, если бот уже работает: **бот в MAX не может написать первым.** Это
устройство их платформы, а не настройка. Заявки из Звонобота и с сайта приносят телефон, а не
ник, — без аккаунта эта половина воронки в MAX недостижима.

## Чем это отличается от Telegram

| | Telegram | MAX |
|---|---|---|
| Протокол | MTProto через TDLib | вебсокет и JSON, внутренний протокол их веб-клиента |
| Прокси | обязателен, зарубежная машина | **не нужен**, MAX доступен с сервера напрямую |
| Сессия | каталог на диске | строка токена в `.env` |
| Документация | официальная | её нет; коды операций выяснены по открытым реализациям |

Последняя строка — главный риск канала. **Протокол может измениться молча**, вместе с их
веб-клиентом. Поэтому: незнакомый кадр не выбрасывается, а сохраняется целиком в `payload`
реплики, а всякий обрыв и отказ входа попадают в журнал как ошибка, а не как тишина.

## Что нужно завести один раз

1. **Настоящая SIM.** Виртуальный номер и номер из сервиса SMS-активации не годятся: у MAX
   чёрные списки таких пулов, регистрация на них — бан в первые сутки. Годится тот же
   корпоративный номер, на котором работает Telegram-аккаунт.
2. **Аккаунт в MAX на этот номер**, с заполненным профилем: имя вида «Бизнес-Прорыв | Аня и
   Катя», аватар, описание. Заполнить **до** первого сообщения клиенту.
3. **Идентификатор устройства** — один раз и навсегда: `uuidgen`. Меняющийся при каждом
   запуске выглядит для их антифрода как вход с нового устройства, а это ровно тот признак,
   за который ограничивают.

## Настройки в `.env`

```
MAX_ACCOUNT_DEVICE_ID=<uuidgen, один раз и больше не менять>
MAX_ACCOUNT_PHONE=+7XXXXXXXXXX
MAX_ACCOUNT_TOKEN=<появится после входа>
MAX_ACCOUNT_DEVICE_NAME=Бизнес-Прорыв CRM
```

Канал включается наличием `MAX_ACCOUNT_DEVICE_ID`. Токена в начале нет — так и надо: сначала
включают канал, потом входят. `pnpm env:check` проверяет номер и идентификатор устройства.

Необязательное, на случай, когда их клиент уедет вперёд: `MAX_ACCOUNT_APP_VERSION`,
`MAX_ACCOUNT_USER_AGENT`, `MAX_ACCOUNT_WS_URL`. Менять их — способ починить канал без
выкладки кода.

## Вход

**На том же сервере, где аккаунт будет работать.** Их антифрод смотрит, откуда входили, и
вход с ноутбука с последующей работой из другого места — повод попросить аккаунт подтвердить
себя, а в плохом случае ограничить его.

```bash
cd ~/telegrambot && pnpm max:login
```

Скрипт запросит код, примет его и напечатает строку `MAX_ACCOUNT_TOKEN=…`. Эту строку нужно
положить в `.env` и перезапустить процесс.

**Токен — это полный доступ к переписке.** Место ему только в `.env`: не в журналах, не в
переписке, не в задачах.

## Проверка

```bash
cd ~/telegrambot && pnpm max:status
```

Печатает состояние соединения, номер и идентификатор аккаунта, устройство. Ненулевой код
возврата означает, что канала нет, — на это можно вешать мониторинг.

Отдельно — сверка человека по телефону, она же проверка того самого вызова, ради которого
всё затевалось:

```bash
cd ~/telegrambot && pnpm max:whois +79001234567
```

**Что здесь важно сверить один раз:** совпадает ли идентификатор человека у аккаунта с тем,
что записал бот. Если да — диалог с ботом и диалог с аккаунтом склеятся в одну карточку сами.
Если нет — карточки разъедутся, и понадобится склейка по телефону.

```sql
select external_user_id, username, first_seen_at
  from public.messenger_identities
 where channel = 'max' order by first_seen_at desc limit 20;
```

## Процесс

Отдельный процесс `max-account` в pm2, рядом с ботом, но независимо от него: бот продаёт
билеты, и его падение стоит денег, а аккаунт держит постоянное соединение по чужому
протоколу.

```bash
pm2 start deploy/run-max-account.sh --name max-account --cwd ~/telegrambot
pm2 save
pm2 logs max-account --lines 50 --nostream
```

**Экземпляр должен быть ровно один.** Вторая копия на том же токене — второе устройство в их
антифроде.

Что делает процесс:

- **пишет входящие в общую ленту переписки** с пометкой `transport: 'account'` — для человека
  бот и живое имя два разных собеседника, и в карточке это две ветки;
- **отправляет ответы менеджера** из общей очереди, отобранные по каналу и транспорту;
- **забирает вложения**: картинки по ссылке из кадра, файлы — спросив временную ссылку.

Групповые чаты в переписку не попадают: тип чата спрашивается отдельно, и всё, кроме диалога,
пропускается. Групповое сообщение в карточке человека — это чужой разговор.

### Ответ из панели

Ветка «MAX · аккаунт» в карточке принимает ответ обычным полем. Ветка «MAX · бот» помечена
«только чтение» и поля ответа не имеет — отвечает аккаунт. Запрет стоит и на сервере: панель
прячет поле, а отказывает база, в той же транзакции, что и постановка в очередь.

Из вложений аккаунт пока отправляет **только картинки** — ровно как бот. Загрузка файлов у
MAX устроена сложнее (адрес, загрузка, ожидание отдельного события «файл готов»), и писать
это вслепую, не проверив на живом аккаунте, значит завести молчаливо ломающийся путь там, где
менеджер ждёт доставки. Документ в ответе честно отказывается с первой попытки.

## Если канал молчит

Молчание вебсокета выглядит одинаково при обрыве и при отсутствии писем — поэтому смотреть
надо не на ленту, а на журнал:

```bash
pm2 logs max-account --lines 100 --nostream | grep "канал MAX"
```

- `связи нет` — обрыв, процесс переподключается сам с нарастающей паузой;
- `вход отвергнут` — токен просрочен, отозван или аккаунт ограничен. Само не починится:
  нужен новый `pnpm max:login`, а если код не приходит — аккаунт ограничен;
- ошибки вида «MAX не ответил на вызов» подряд — скорее всего, у них поменялся протокол.
  Первое, что стоит попробовать, — поднять `MAX_ACCOUNT_APP_VERSION` до версии их текущего
  веб-клиента.

## Выход и смена номера

```bash
cd ~/telegrambot && pnpm max:login --forget
```

Завершает сессию на их стороне и просит убрать `MAX_ACCOUNT_TOKEN` из `.env`. Порядок именно
такой: забытый токен без выхода оставляет живой вход в списке устройств, который потом некому
закрыть.

История переписки при этом остаётся у нас — она в нашей базе, а не у них.

## Если аккаунт заблокировали

1. **Не входить повторно с того же места по кругу** — это ухудшает положение.
2. Переписка не потеряна: она в нашей базе, вместе с вложениями.
3. Разговор продолжается через Telegram-аккаунт, а покупка билетов — через бота MAX, он
   работает независимо и от блокировки аккаунта не страдает.
4. Восстановление — через поддержку MAX. Аккаунт привязан к личности, и «купить новый номер»
   тут не работает так, как в Telegram.
