# Статусы и категории пользователей

## Перед включением

1. Применить миграцию `20260728200000_user_statuses_categories`.
2. Открыть `/classification` под администратором с `users.read`.
3. Для создания и изменения каталога проверить наличие `users.write`.
4. Создать необходимые категории до добавления `add_category` в сценарий.
5. Для статуса проверить группу взаимоисключения и допустимые переходы.
6. Сохранить черновик сценария и убедиться, что сервер не возвращает
   `USER_CLASSIFICATION_CONFIGURATION_INVALID`.
7. Опубликовать новую версию сценария с правом `scenarios.publish`.

## Payload узлов

```json
{
  "statusCode": "interested",
  "reason": "Пользователь заинтересовался предложением"
}
```

```json
{
  "categoryCode": "event_interest",
  "reason": "Пользователь выбрал мероприятие"
}
```

Код состоит из строчных латинских букв, цифр и подчёркиваний, начинается с буквы и имеет длину
от 2 до 64 символов. Причина содержит от 3 до 200 символов. У каждого узла должен быть ровно
один автоматический переход.

## Нормальное поведение

- `set_status` оставляет без изменений уже активный такой же статус.
- Новый статус закрывает только активный статус из той же группы взаимоисключения.
- Если предыдущий статус задаёт список переходов, новый код обязан входить в этот список.
- `add_category` добавляет категорию, не снимая остальные категории.
- Повторное добавление уже активной категории не создаёт вторую запись.
- Назначения хранят источник `scenario`, стабильную ссылку на сессию и узел, причину и снимок
  отображения.
- Карточка пользователя показывает активные статусы, категории и последние записи истории.
- Оператор с `users.write` может назначить или снять значение из карточки пользователя. Причина,
  история, outbox и `audit_log` фиксируются в одной транзакции.

## Диагностика

- Публикация отклонена: проверьте, что код существует и активен в `/classification`.
- Runtime сообщает о недоступной классификации: проверьте каталог и применённую миграцию; не
  изменяйте назначение ручным SQL.
- Переход статуса отклонён: проверьте `allowedTransitionCodes` предыдущего активного статуса.
- Возник конфликт версии: перечитайте каталог и повторите изменение с актуальным `lockVersion`.
- Повтор создал неожиданный результат: найдите назначение по пользователю, коду и активному
  интервалу, затем проверьте ссылку источника. Не удаляйте историю.

## Ограничения текущего этапа

Правила классификации по оплате, опросам и импорту и массовые операции ещё не реализованы.
Каталог, ручные операции, автоматические действия сценария, сегменты, подготовка рассылок,
проверка публикации и чтение истории готовы.
