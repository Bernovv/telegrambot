# Управление сценариями мероприятия

## Область

- `GET /api/v1/events/:id` возвращает историю сценария с узлами, переходами и ошибками.
- `POST /api/v1/events/:id/scenario-drafts` создаёт или обновляет единственный черновик.
- `POST /api/v1/events/:id/scenario-versions/:versionId/publish` публикует проверенный черновик.
- `/events/:id/scenario` предоставляет структурированный редактор в админке.

Операции не публикуют само мероприятие. Пользовательские сессии запускаются отдельным runtime
только после назначения опубликованной версии мероприятию.

## Порядок публикации

1. Оператор с `events.write` сохраняет черновик и указывает причину.
2. API проверяет boundary-схему и сохраняет граф вместе со списком ошибок.
3. Оператор исправляет все ошибки серверной проверки.
4. Оператор с `scenarios.publish` указывает причину публикации.
5. API повторно читает версию и проверяет граф.
6. PostgreSQL получает advisory lock `event-sales:<eventId>` и блокирует мероприятие.
7. Транзакция повторно проверяет статус черновика и `expectedLockVersion`.
8. Версия становится `published`, назначается мероприятию, версия агрегата увеличивается один раз,
   audit добавляется в той же транзакции.

Для узла `wallet_credit` редактор создаёт безопасный шаблон payload с бонусом 100 ₽. Перед
публикацией оператор обязан проверить сумму в строке целых копеек, валюту, назначение бонуса и
уникальный для бизнес-правила `idempotencyKeyTemplate`. Сервер ограничивает одно начисление
10 000 ₽, разрешает только bucket `bonus` и требует один автоматический переход.

Для `set_status` и `add_category` оператор выбирает стабильный код из каталога классификации и
указывает причину. Сервер требует один автоматический переход и перед сохранением и публикацией
проверяет, что каждый используемый статус или категория существует и активен. Каталог
администрируется отдельно на `/classification`.

После commit изменить или удалить опубликованную версию, её узлы либо переходы запрещает триггер.

## Ошибки

- HTTP 400: проверить UUID, payload узлов, размеры графа, причину и optimistic version.
- HTTP 404 `ADMIN_SCENARIO_VERSION_NOT_FOUND`: обновить карточку и проверить выбранную версию.
- HTTP 409 `ADMIN_EVENT_VERSION_CONFLICT`: перечитать мероприятие перед повторной записью.
- HTTP 409 `ADMIN_SCENARIO_VERSION_NOT_DRAFT`: версия уже неизменяема.
- HTTP 422 `ADMIN_SCENARIO_VALIDATION_FAILED`: исправить перечисленные ошибки графа.
- HTTP 403 на публикации: выдать роль с `scenarios.publish` через контролируемый RBAC-процесс.

Не исправлять опубликованные версии ручным SQL. Rollback в будущем создаёт новую версию-копию,
а не меняет старую.

## Миграция

Перед включением маршрутов применить `20260726120000_scenario_versions`. Для пользовательского
runtime дополнительно применить `20260726160000_scenario_runtime`, а для `wallet_credit` —
`20260728160000_scenario_wallet_credit`. Для `set_status` и `add_category` применить
`20260728200000_user_statuses_categories`. Проверить чистое применение и обновление с предыдущей
схемы. Миграции не изменяют существующие финансовые строки.
