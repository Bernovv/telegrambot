# MAX как канал внутри общего api

MAX перестаёт быть отдельным приложением со своей базой и становится вторым каналом рядом с
Telegram: один процесс `api`, одна база, один разговорный слой, одна очередь доставки.

## Что где

| Что | Где |
|---|---|
| Разговорный слой (общий на оба мессенджера) | `packages/messenger-core/src/conversation-controller.ts` |
| Транспорт MAX | `packages/messenger-max` |
| Вебхук | `POST /webhooks/max/<секрет>` в `apps/api` |
| Отправка уведомлений | `MaxNotificationSender`, подключается в `apps/worker` |
| Канал заказа | `orders.channel` — по нему билет уходит в тот же мессенджер |

Разговорный слой один намеренно. Сценарий покупки, ограничение по телефону, партнёрская
программа и бонусы у двух мессенджеров одинаковые; вторая копия означала бы, что каждая
правка делается дважды, а расходиться они начнут на третьей. Своим у канала остаётся то,
что действительно своё: как приходит обновление, как выглядит кнопка и как уходит ответ.

Коды кнопок у каналов совпадают (`buy_ticket`, `ticket_vip`, `my_bonuses`) — они живут в
общем контенте.

## Включение

**Пока `MAX_BOT_TOKEN` пуст, канал не поднимается вовсе.** Это не забывчивость, а
обязательное состояние до переезда: старый MAX-бот ещё работает на своей базе, и два
приёмника на одни обновления означают двух собеседников у одного человека.

Порядок включения — только после того, как старый бот остановлен:

**1. Секреты.**

```bash
openssl rand -hex 24   # MAX_WEBHOOK_PATH_SECRET
openssl rand -hex 24   # MAX_WEBHOOK_SECRET
```

В `.env`: `MAX_BOT_TOKEN`, `MAX_BOT_USERNAME`, `MAX_WEBHOOK_PATH_SECRET`,
`MAX_WEBHOOK_SECRET`.

**2. Сертификат Минцифры.** `platform-api2.max.ru` отдаёт сертификат, которому Node по
умолчанию не доверяет, — тот же случай, что у Т-Банка. Переменная читается Node **до старта
процесса**, поэтому в `.env` её класть бесполезно: она нужна в окружении `pm2`.

```bash
sudo ls -l /home/maxbot/max-bot/certs/russian_trusted_ca.pem
```

```bash
cd ~/telegrambot && NODE_EXTRA_CA_CERTS=/home/maxbot/max-bot/certs/russian_trusted_ca.pem pm2 restart api worker --update-env
```

Без неё всё выглядит как безымянный сетевой сбой; чтобы этого не повторялось, ошибка
транспорта MAX теперь называет причину и прямо упоминает `NODE_EXTRA_CA_CERTS`.

**3. nginx** — открыть наружу ровно этот путь на хосте вебхуков:

```nginx
location ~ ^/webhooks/max/[A-Za-z0-9_-]+$ {
    proxy_pass http://127.0.0.1:3001;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

**4. Остановить старый бот** — иначе он продолжит отвечать тем же людям:

```bash
systemctl stop max-bot && systemctl disable max-bot
```

**5. Перезапустить процессы и подписаться на вебхук.** Подписка перенаправляет обновления
MAX на нас, поэтому идёт последней:

```bash
cd ~/telegrambot && pm2 restart api worker && pnpm max:subscribe
```

Адрес вебхука целиком является секретом — в переписку и в задачи он попадать не должен.

## Что проверить в первый же день

**Диалог целиком:** запуск бота, «Программа и тарифы», «Купить билет», выбор тарифа, ввод
количества, оферта, оплата, билет. Билет — главное: он приходит картинкой с QR, а картинка
в MAX загружается тремя запросами вместо одного.

**Куда уходят билеты.** Заказ помнит свой канал, и доставка идёт по нему:

```sql
select o.channel, count(*), max(o.created_at)
  from public.orders o
 where o.created_at > now() - interval '1 day'
 group by o.channel;
```

```sql
select recipient_channel, status, count(*)
  from public.notification_deliveries
 where created_at > now() - interval '1 day'
 group by recipient_channel, status;
```

**Застрявшая доставка** видна обычным способом: `pnpm queue:dead-letter`.

## Чего здесь нет и почему

- **Клиентской библиотеки MAX.** От их API нужны четыре вызова — это полсотни строк;
  библиотека тянет свою модель бота, свой роутер, свой цикл опроса и обработчик ошибок,
  который по умолчанию завершает процесс. Со всем этим в старом боте уже пришлось бороться.
- **Проверки тела вебхука схемой.** Формат MAX описан хуже телеграмного, а незнакомый тип
  обновления — обычное дело. Отвергнутое обновление они повторят несколько раз и бросят —
  вместе с человеком, который написал боту. Принимаем всё, разбирает транспорт.
- **Подмены канала при доставке.** Идентификаторы человека в Telegram и в MAX — оба числа.
  Отправка «максового» получателя телеграмным отправителем означала бы чужой билет
  постороннему с тем же номером. Нет отправителя для канала — доставка падает и уходит в
  повтор, а не «доставляется как-нибудь».

## Что осталось до полного объединения

1. **Перенос боевых данных MAX** — фаза 4 плана, единственный необратимый шаг. Делается
   отдельным скриптом с сухим прогоном на копии базы.
2. **Тексты.** Сейчас общий контент — телеграмный. Переделывается один раз на оба канала.
3. **Колонка «Канал»** в списках панели: данные для неё уже есть (`orders.channel`,
   `messenger_identities.channel`), экрана пока нет.
4. **Гашение старой панели MAX** — после недели параллельной сверки сумм и балансов.
